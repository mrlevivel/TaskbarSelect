# Native administrator bootstrap build

Use 64-bit Windows PowerShell 5.1 and the included Windows .NET Framework compiler. `Build.ps1` now builds the separate managed administrator payload, embeds its exact configuration and SHA-256 into a native bootstrap, statically validates that bootstrap, and embeds the bootstrap and payload hash into the normal Taskbar Select EXE. The app retains its normal production branding and asInvoker manifest. Building does not install or launch Taskbar Select, request UAC, or change Startup.

```powershell
.\Build.ps1 -OutputDirectory C:\TaskbarSelect-build
```

The native toolchain is portable Zig **0.15.2**, from the publisher's exact Windows x86_64 ZIP. `build/Get-NativeCompiler.ps1` verifies its pinned 92,614,574-byte size and SHA-256 `3a0ed1e8799a2f8ce2a6e6290a9ff22e6906f8227865911fb7ddedc3cc14cb0c`, then compares the extracted compiler EXE with that verified archive entry. It does not install Zig or add it to PATH. The cache must be an absolute path outside the source checkout. Choose it explicitly when needed:

```powershell
.\build\Get-NativeCompiler.ps1 -CacheDirectory C:\TaskbarSelect-build-tools
.\Build.ps1 -OutputDirectory C:\TaskbarSelect-build -NativeCompilerCache C:\TaskbarSelect-build-tools
```

By default the selector uses `TASKBARSELECT_NATIVE_TOOLCHAIN_CACHE`, an existing maintainer validation cache, `RUNNER_TEMP`, or `%LOCALAPPDATA%\TaskbarSelectBuildTools\native-toolchain`. This is separate from the app's settings and installation. CI verifies the same publisher archive in fresh runner-temporary storage and passes the selected cache to later build steps through a job-local environment variable. Download or compiler integrity failures stop the build. An existing extracted local cache is trusted build input: the selector verifies the archive and compiler EXE, but does not rehash every extracted header and library. Release CI starts from the verified archive rather than reusing a maintainer's extracted libraries.

The payload uses `TaskbarSelect.AdministratorPayloadEntry` as its explicit entry point. Shared `Program.cs` dependencies remain compiled, while its normal UI entry is never selected in the payload. The native bootstrap uses `BootstrapEntry`, has no CLR or CRT startup, statically imports only Kernel32, and loads other system libraries through its restricted native policy. Its native version resource matches the payload's file/product versions, identifies the executable as “Taskbar Select administrator support,” and includes the app's own icon. Both C# assemblies and the native C build treat warnings as errors. The managed assembly's default P/Invoke search is restricted to System32.

`AdministratorPayload.config` is an exact one-line UTF8 file without a BOM and with one terminal LF; its narrow `.gitattributes` rule preserves those bytes on Windows checkout. Generated payload EXE, header, configuration bytes/hash, resource object, bootstrap and compiler caches are build outputs. The portable package and installer still contain only the normal app EXE and their explicitly allowlisted documentation; these generated files/toolchains are not separate shipping assets.

Static build checks inspect the linked bootstrap's x64/GUI entry, ASLR/NX flags, absent CLR/delayed-import directories and single Kernel32 import descriptor. The native `--bootstrap-self-test` mode is a content-free check of the embedded parser/configuration/environment policies; it validates its own token and can run under either a standard local build or an elevated hosted runner. It does not create a cache, start a managed payload or request UAC.

The normal app first creates its pinned native approval host suspended at medium integrity, verifies its physical image and creation time, then resumes it. The host pins its source and creates a private, sealed drive namespace before loading additional Windows libraries or requesting UAC. The elevated bootstrap independently verifies its medium-integrity parent, seals its own private namespace, and waits for authenticated grants before creating a protected cache and suspended managed payload. The payload belongs to a kill-on-close job and receives the retained private map explicitly before authorization/resume. Windows does not inherit that map into child processes. The helper verifies its assigned namespace before worker launch; workers use the native-admitted default HIGH/global map, whose physical targets and denial of MED mutation remain pinned for the session. These checks affect only the owned processes; the launcher does not change shared drive mappings or Windows security settings.

The internal `--approval-self-test <nonce> <parent-pid> <parent-utc-ticks>` entry exercises the medium-integrity approval-host setup and a fixed, unelevated native child. The managed launch tests provide these authenticated arguments from a genuine medium-integrity parent; it is not a no-argument contributor build switch. It does not request UAC or create the protected managed payload. Actual administrator execution requires a high token and authenticated medium-integrity parent of the same user/session. The hosted boundary fixture is designed to exercise the real approval-host/runas route and worker lifecycle. A successful build or standard-permission self-test is not proof of actual elevated payload-map assignment, worker execution, interactive UAC, cancellation, cleanup, or disposable installer validation. The running controller and Windows/admin-controlled policy are trusted; these checks do not contain malware already controlling that controller or account.
